# Contributing to subtext-scan

The most useful contributions are new hiding techniques with a fixture that proves the scanner catches them, and benign documents that it flags wrongly.

## Before opening a change

For a new detector, a changed severity rule or a new output field, open an issue first. Small fixes can go straight to a pull request. Keep every example synthetic. Do not commit real documents, customer data, third-party copyrighted files or secrets.

## Local verification

You need Node.js 22.13 or newer.

```bash
npm ci
npm test
npm run typecheck
```

## Fixtures

Every file under `fixtures/` is generated by `scripts/generate-fixtures.mjs`, and CI fails if regenerating changes a byte. To add a case:

1. Build the file in the generator, next to similar cases. Draw it with pdf-lib, or write the raw XML or HTML.
2. Record what it must produce: `kind` (`malicious` or `benign`), the expected `max` severity, and the findings that must appear (`rule`, and optionally `mechanisms`, `page`, `phrases`, `severity`).
3. Run `npm run fixtures && npm test`.

A false positive is fixed with a benign fixture and a change that makes it pass, without breaking any malicious fixture.

## Phrase rules

Add an attack example to `tests/phrases.test.mjs` for every new or changed rule. If the rule could plausibly match ordinary business text, add that text to the list of ordinary sentences that must not match.

## Pull requests

Explain the technique or false positive, include the fixture, and leave `npm test` green. Keep unrelated refactors out of the same change.
